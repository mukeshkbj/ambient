# Research report: grounding for the `caller` adapter and the deletions

I read the code and ran no tests, because `node_modules/` is absent. I edited, committed and created nothing in the repo. Lines marked "(L0)" are from `lane/L0-p0`. Two corrections to the brief: `RuntimeState` is `"online" | "offline" | "unknown"` (`src/types.ts:3`), so the string `'disconnected'` does not exist. The installed Node is v26.7.0.

## 1. Run lifecycle (`src/conversations.ts`)

**`ask()` (184–228)**
- It rejects empty text (186).
- It calls `ensureConversation` (389–406), which creates a session through `assistant.createSession()` and a numbered title.
- It rejects with "already has active work" if the conversation has a run in `queued`, `accepted`, `running`, `waiting_approval`, `cancel_requested` or `unknown` (188–190, and again at 192). The query is `store.activeRunForConversation`, `store.ts:415–422`.
- `ensureLive` (414–427) resumes the session if there is no live id.
- It inserts the run as `queued` (196–207).
- It calls `assistant.submitPrompt(liveSessionId, instruction)` (210).
- If the run is still `queued`, it becomes `running` when `SubmitResult.state === "streaming"` and `accepted` otherwise (212–217).
- If the submit throws, the run becomes `failed` and the error is rethrown (220–225).
- It returns `waitForRun(run.id, options.waitMs ?? 0)` (227).

**`waitForRun` (234–254)**
- It is event-driven. It returns early when the status is in `SPEAKABLE` (27): `completed`, `failed`, `cancelled`, `waiting_approval`, `unknown`.
- Otherwise it waits for `waitMs`, then resolves with the latest view.
- The MCP and Alexa callers pass `askWaitMs`, which defaults to 6000 ms (`config.ts:32`).

**`applyEvent` (332–387)**
- It resolves the active run by `(runtimeId, event.sessionId)` via `store.activeRunByLiveSession` (`store.ts:406–413`, which includes `unknown`).
- It ignores events with no `sessionId` or no active run (333–335).
- It ignores events for terminal runs (335).

**Events and status changes**

| Event | Effect | Line |
|---|---|---|
| `message.start`, `message.delta`, `message.interim`, `tool.start`, `tool.complete`, `status.update` | `queued` or `accepted` becomes `running`. `progress` is set from `text`, `summary` or `message`, else `name`. Nothing else changes status. A `status.update` on an `unknown` run leaves it `unknown`. | 379–386 |
| `approval.request` | Builds an `Approval` and stores it. Run becomes `waiting_approval`, with `progress` set to description or command. | 338–363 |
| `message.complete` | Becomes `cancelled` if the run was `cancel_requested`. Becomes `failed` if `payload.status === "error"` or `payload.error` is set. Becomes `cancelled` for `status` `cancelled` or `canceled`. Otherwise `completed`. Also resolves all approvals for the run. | 364–377 |

**`approval.request` creating the row (338–363)**
- The `requestId` is required. Without one, only `progress` is updated (339–343).
- If a row exists with the same `(runtimeId, requestId)` and it is resolved, the event is ignored (344–345).
- The row id is `${runtimeId}:${requestId}` (347).
- `command` defaults to `"<label> requested approval"` (353). `description` is optional. `choices` defaults to `["once","deny"]` (355–357).
- `store.createOrUpdateApproval` (`store.ts:499–521`) upserts on `UNIQUE(runtime_id, request_id)` and resets `resolved_at` to NULL on conflict.

**Other transitions**
- `respondToApproval` (304–330):
  - The decision type is `"once" | "deny"` only.
  - It rejects an unknown or already-resolved approval, a concurrent response for the same request (310), and a run in `unknown` (312).
  - It calls `assistant.respondToApproval(approval.liveSessionId, approval.requestId, decision)` (315). A `resolved < 1` result throws (316–318).
  - It marks the approval resolved (319).
  - It moves the run to `running` only if the status is still `waiting_approval` (323–325).
- `steer` (275–287):
  - It rejects terminal runs (277), `unknown` (278), empty text, and adapters without `steer`.
  - It calls `assistant.steer(run.liveSessionId, text)`.
  - It moves `queued` or `accepted` to `running`.
  - It has no `waiting_approval` guard. Steering during a pending approval is allowed and does not resolve the approval.
- `cancel` (289–302):
  - A terminal run is returned as is.
  - It rejects `unknown`.
  - It calls `assistant.interrupt()`. A result of `"interrupted"` gives `cancelled` and resolves approvals (300). Any other result gives `cancel_requested`.
  - From `cancel_requested`, only a later `message.complete` finishes the run (367–368).
- Disconnect (82–88):
  - The adapter's `onConnectionState("offline")` calls `store.markActiveRunsUnknown(runtimeId, …)` (`store.ts:434–440`).
  - This is runtime-wide. It hits every run in `queued`, `accepted`, `running`, `waiting_approval` or `cancel_requested` for that runtime id. `unknown` runs are not re-marked.
  - Any other state value only calls `setRuntimeState`.
- Other ways to reach `unknown`:
  - `onReplayGap` is per live session (89–99).
  - `reconcilePendingApprovals` is invoked from `discover` and `ensureLive` (429–456).
  - `registry.startAll` marks all active runs `unknown` on process start (`registry.ts:235–243`).
- Leaving `unknown`:
  - A `message.complete` still applies, because `unknown` is non-terminal.
  - `mergeActiveSession` flips `unknown` runs back to `running` when `listActiveSessions` reports `working` or `starting` (488–490).

**`RunStatus` list (`src/types.ts:5–14`)**

| Status | How a run gets there |
|---|---|
| `queued` | Row created at `ask`. |
| `accepted` | Submit returned a state other than `streaming`. |
| `running` | Submit returned `streaming`, a progress event, a steer, or an approval response. |
| `waiting_approval` | `approval.request`. |
| `completed`, `failed`, `cancelled` | `message.complete` (see above). |
| `cancelled` | Also `interrupt` returned `interrupted`. |
| `cancel_requested` | `interrupt` returned something else. |
| `unknown` | `offline`, replay gap, reconcile, or restart. |

**Assumptions that break for a 2–10 minute call with several approvals**
1. **Race on the second approval.** The `waiting_approval` to `running` reset (323) checks only the current status. If a second `approval.request` lands while the first `respondToApproval` is awaiting the adapter ack, the status is `waiting_approval` again (set by the new request). The reset then flips the run to `running` while a new open approval exists.
   - `registry.needsAttention()` (`registry.ts:158`) and the status-driven Alexa and sim flows key on `status === "waiting_approval"`. They would miss the second approval.
   - The same `store.view()` path attaches only the first open approval of a run (`store.ts:551–556`, and `recentRunViews` 393).
2. **No path from an event to `unknown`.** `message.complete` maps only to `completed`, `failed` or `cancelled` (364–377). Any status string other than error or cancelled becomes `completed`, including a hangup with no confirmation.
   - The plan's "call ended without a confirmation → `unknown`" has no event route. The only routes are runtime-wide `offline` and per-session `onReplayGap`.
   - Parallel calls on one runtime id would all go `unknown` when any one signals `offline`.
3. **Request ids must be unique per ask.** A reused `requestId` whose row is resolved is silently ignored (344–345).
4. **`approval.request` has no status guard.** It overwrites `cancel_requested` with `waiting_approval` (361).
5. **`steps` is capped at 30 entries.** `updateRun` appends `progress` to `steps` only when it changes, then slices to the last 30 (`store.ts:478–482`).
   - A 10-minute transcript streamed as `message.delta` or `status.update` overwrites `progress` and keeps only the last 30 lines.
   - Each event rewrites the row and emits a change event.
   - `store.appendTranscript` and `transcript` exist (`store.ts:558–572`), but only the Bedrock adapter uses them.
6. **One active run per conversation** (188). Reaching `steer` through MCP `delegate` depends on this: an active run turns `delegate` into a steer (`mcp.ts:119–126`).
7. **The answer channel is binary.** `respondToApproval` carries only `once` or `deny`. Free text such as "160" can reach the adapter only through `steer`.
8. **Elicitation only lives inside a tool call.** MCP elicitation (`mcp.ts:69–98`) runs only while a `delegate` or `status` call is in flight, bounded by `askWaitMs` (6000 ms). A decision arriving minutes later has no elicitation channel.
   - L0 moves it onto the call's own SSE stream (`relatedRequestId`, `oneOf` schema).
   - The sim auto-declines an open elicitation after 60 s (`sim.ts:90–95`).

## 2. Registration and config

**`src/runtimes/registry.ts`**
- `ADAPTERS` (413–418) maps `{hermes, demo, bedrock, openclaw}` to factories `(item, env, store, dataDir?) => RuntimeEntry`.
- `buildRuntimeRegistry` (420–433) throws `Assistant adapter "x" is not available; supported: …` for an unknown adapter (428).
- `polledRuntime` (338–355) is the shared pattern for connectionless adapters: `engineFor` plus a `discover` on start and every 30 s, with `client.close?.()` on close. `demoRuntime` (392–398) and `bedrockRuntime` (400–411) use it.
- `numberOption` (329–335) reads `item.options` values as positive numbers.
- `entryFor` builds the descriptor `{id, label, kind, adapter: item.adapter, capabilities}` (313–327).
- `RuntimeEntry` is `{descriptor, client, engine, start, close, connector?}` (11–18).

**`src/config.ts`**
- `RuntimeEntrySchema` (5–15): `id`, `label`, `kind` (default `local`), `adapter` (default `"hermes"`), optional `endpoint`, `tokenEnv`, `connectorTokenEnv`, `options: Record<string,string>`, `default`.
- All `options` values are strings. A new adapter's config is `options.*` plus a `tokenEnv`-style env name, or its own env vars.
- `EnvSchema` (19–44) has no Twilio, Anthropic or Alexa-proactive keys. It does have `ALEXA_SKILL_ID`, `ALEXA_VERIFY_SIGNATURE`, `PUBLIC_BASE_URL` and `AMBIENT_ASK_WAIT_MS`.
- `runtimeEntries` (71–95) reads `AMBIENT_RUNTIMES_FILE` or `$AMBIENT_DATA_DIR/runtimes.json`. It prepends a Hermes entry from `HERMES_WS_URL` or `CONNECTOR_TOKEN` (81–90). It throws "At least one runtime is required: set HERMES_WS_URL/CONNECTOR_TOKEN or …" when empty (91–93).
- On L0, `AMBIENT_HOST` (default `0.0.0.0`) and `host` are added at lines 21, 49 and 129.

**Config files and scripts**
- `runtimes.demo.json` has `planner` (demo, default) and `coder` (demo, `options.script: "deploy"`).
- `runtimes.bedrock.json` has `nova` (bedrock, default) and `planner` (demo).
- `runtimes.example.json` has `nova`, `hermes`, `hermes-cloud`, `openclaw` and `planner`.
- `package.json` scripts:
  - `demo` is `AMBIENT_RUNTIMES_FILE=runtimes.demo.json ALLOW_UNAUTHENTICATED=true tsx src/server.ts` (L0 prepends `AMBIENT_HOST=127.0.0.1`).
  - `dev:bedrock` is the same with `runtimes.bedrock.json`.
  - Others: `dev`, `check:hermes`, `check:hermes-contract`, `check:mcp-contract`, `check:runtime`, `connector`, `smoke:mcp`, `latency`, `scan`, `infra:*`.
- `.env.example` has no Twilio or Anthropic keys. It lists `HERMES_*`, `CONNECTOR_TOKEN`, `AMBIENT_BRIDGE_URL`, `OPENCLAW_TOKEN` and `AWS_*`.

**Minimum to add the `caller` adapter**
- A `caller: callerRuntime` factory entry in `ADAPTERS` (`registry.ts:413`) that returns `polledRuntime(item, env, store, client)`, with `client.close()` for hanging up open calls.
- Its options and secrets come from `item.options` or `env` (`item.tokenEnv` style).
- A `runtimes.*.json` entry `{id, label, kind, adapter: "caller", options…}`.
- Because `adapter` is a plain string, no schema change is needed.
- `ephemeralSessions` (`runtimes/types.ts:96`) is the flag for live ids that die with the process. Hermes, Bedrock and Demo all set `true`.
- `readConfig` has no non-Hermes env fallback. If you drop the Hermes shorthand and no runtimes file exists, it throws (91–93).

**Reaching `steer` with "tell him I can do 160"**
- The only route is `SteerWorkIntent`. In `alexa/interaction-model.en-US.json`, its slot is `instruction: AMAZON.SearchQuery` and its samples are `tell it {instruction}`, `steer the work to {instruction}`, `change the work to {instruction}`, `actually {instruction}`.
- "tell him {instruction}" is not a sample, so that utterance matches no sample and would fall to `FallbackIntent` or another intent. The en-GB model has the same samples.
- The handler needs a work id. It reads the slot or the session attribute `lastWorkId` (141–143). `runAttributes` sets `lastWorkId` after any ask, status, approval or steer (186–194).
- In a fresh session (for example one opened by a proactive notification), `lastWorkId` is absent and the response is "Which work should I steer?" (342). Unlike `GetLastWorkIntent`, there is no fallback to `registry.latestRun()` or `needsAttention()`.
- `engine.steer` then runs as in section 1. A `waiting_approval` run stays pending after the steer.

**Surprise (found in passing):** `lastApprovalId` treats the slot `about` as an explicit approval id (145–147). `RespondApprovalIntent` in the interaction model has an `about` slot ("{decision} the {about} request"). A phrase like "dinner" therefore goes to `registry.engineForApproval("dinner")`, which resolves no runtime and throws "Approval is no longer pending".

**`alexa-verify` wiring**
- It is applied only in `server.ts:373–380`, when `dependencies.alexa.verifySignature` is true, before `handleAlexaRequest`.
- The `alexa` dependency object exists only when `config.alexaSkillId` is set (`server.ts:506–512`). Otherwise `/alexa` returns 404 (369–372).
- `verifySignature` comes from `ALEXA_VERIFY_SIGNATURE`. The CDK stack sets it to `true` (`infra/stack.ts:84`).
- The verifier is `alexa-verify.ts:60–117`: cert URL pinned to `s3.amazonaws.com/echo.api/`, SAN `echo-api.amazon.com`, chain check, RSA-SHA256 over the raw body, timestamp within 150 s.
- Repo-wide grep for `proactive`, `twilio`, `anthropic` and `ConversationRelay` in `src`, `test`, `scripts`, `infra`, `alexa` and `package.json` finds nothing.

## 5. Sim

**How the sim talks to `/mcp`**
- `SimHost` (`sim.ts`) is a real MCP `Client` over Streamable HTTP to `mcpUrl` (`http://127.0.0.1:${port}/mcp`), with the bearer token if `accessToken` is set (71–79).
- It declares `elicitation` capability and answers `ElicitRequestSchema` by emitting an `elicit` SSE event. It holds the request until `answerElicit` or 60 s (83–97).
- `watch()` (114–142) subscribes to every engine's `onRunChanged` and emits `run` events with a task-shaped `view`, plus `attention` events. Approvals are `{agent, command, description?}` (133–135).
- `callTool` (185–206) calls the MCP tool. If `_meta.ui.resourceUri` starts with `ui://`, it also `readResource`s the HTML.
- `turn(utterance)` (208–219) is `route` then `callTool`. `route` (173–183) is `bedrockRoute(...) ?? keywordRoute(...)` from `sim-router.ts`.
- `readResource` (222–228) and `asset` (231–237) serve `ui://` HTML and `web/sim/` files.

**HTTP endpoints (`server.ts:289–358`)**
- `/sim/api/events` (SSE), `/sim/api/turn`, `/sim/api/tool`, `/sim/api/resource`, `/sim/api/elicit`, and static assets.
- L0 adds auth on `/sim/api/*` (L0 `server.ts:291–294`).
- `startFromEnvironment` constructs `SimHost` (518–525) and calls `sim.watch()`.

**`web/sim/index.html` (283 lines)**
- It posts utterances to `/sim/api/turn` (163) and renders `speech`, `ui.html` and `structuredContent`.
- It loads `ui://` HTML into an iframe via `loadView`, and acts as an MCP-Apps host for `ui/initialize` and `tools/call` (185–231).
- It subscribes to SSE (234–246), auto-opens `ui://ambient/task` through `/sim/api/resource` (259–265), and has a `refreshDashboard` path calling the `dashboard` tool (242, 254–258).
- Devices: voice-only, mobile, echo-show-8, echo-show-15, fire-tv (`DEVICES`, 104–110).

**What changes if `sim-router.ts` and `dashboard.ts` are deleted**
- **`sim-router.ts`.** `sim.ts:5` imports `bedrockRoute`, `keywordRoute` and `RoutedCall` (type used at 20, 173–183, 210). `SimHost.route` and `turn` lose their utterance-to-tool mapping.
  - `/sim/api/turn` and the page's typed/spoken input (`send()`, `index.html:158–171`) depend on it. `keywordRoute` was the zero-key path. No test covers it.
  - The page does not read `routed`.
- **`dashboard.ts`.** It exports three things: `dashboardSnapshot`, `DASHBOARD_HTML`, and **`TASK_HTML`** (122–…). The task card HTML is in the same file.
  - `mcp.ts:6` imports all three. The `dashboard` tool is at 367–382, the dashboard resource at 384–390, and the task resource at 392–398 (`TASK_HTML`).
  - `voice.ts:90` defines `DASHBOARD_RESOURCE_URI`. `voice.ts:126` points every `runResult` at `TASK_RESOURCE_URI` (`ui://ambient/task`).
  - The sim's task card (`index.html:262`) and `pushStructured` depend on `TASK_HTML`. Deleting `dashboard.ts` also deletes the task card unless `TASK_HTML` is moved. `HOST_BOOT` (103) is shared by both HTML blobs.
  - The `dashboard` tool is asserted in `test/mcp.test.ts:39,45` and `test/http.test.ts:66`. The sim has `refreshDashboard` (`index.html:242,254–258`).
  - Docs: `docs/acceptance.md:16,57` and `docs/demo-runbook.md:13,17`.

**Representative snippet (`test/conversations.test.ts:29–51`)**
```ts
  it("projects the real event envelope and responds to the exact approval request", async () => {
    const hermes = fakeHermes();
    const store = new AmbientStore();
    const engine = new ConversationEngine(hermes.client, store, {
      runtime: { id: "local", label: "My Hermes", kind: "local", state: "unknown", updatedAt: "2026-09-06T10:00:00.000Z" },
      now: () => "2026-09-06T10:00:00.000Z",
      id: (() => { let n = 0; return () => `id-${++n}`; })()
    });
    const run = await engine.ask("Restart the demo", undefined, true);
    hermes.emit({
      type: "approval.request",
      sessionId: "runtime-1",
      payload: { requestId: "approval-7", command: "restart demo", description: "Restart it", choices: ["once", "deny"] }
    });
    await new Promise(resolve => setImmediate(resolve));
    expect(engine.getWork(run.id)).toMatchObject({ status: "waiting_approval", approval: { requestId: "approval-7" } });
    await engine.respondToApproval("local:approval-7", "once");
    expect(hermes.client.respondToApproval).toHaveBeenCalledWith("runtime-1", "approval-7", "once");
    await expect(engine.respondToApproval("local:approval-7", "once")).rejects.toThrow("no longer pending");
    store.close();
  });
```
